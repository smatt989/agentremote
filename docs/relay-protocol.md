# Encrypted relay protocol v1

## Trust and data flow

The Mac owns agent processes and local history. Its HTTP API binds only to loopback. The Mac makes an outbound connection to `wss://RELAY/v1/host`; the phone connects to `/v1/client`. TLS is required except for localhost development. TLS certificate validation remains enabled, and automatic redirects are refused.

The relay can observe routing identifiers, public Mac identity keys, IP addresses, connection times, packet sizes, and availability. It does not receive plaintext requests, file bytes, API bearer tokens, QR secrets, or device encryption keys. It can deny service or delay traffic; end-to-end encryption cannot guarantee relay availability.

## Mac identity

The Mac generates a persistent Ed25519 identity in its private local state. Its routing ID is lowercase SHA-256 of the identity public key in DER SPKI format. On connection the relay sends a random 32-byte challenge. The Mac signs UTF-8:

```text
agent-remote-host/v1\nCHALLENGE_BASE64\nHOST_FINGERPRINT
```

The relay verifies the signature before registering or replacing that host’s socket. The challenge expires after 10 seconds. Claiming another host’s public routing ID without its private key does not establish a connection.

## QR pairing

The local Mac generates a single-use invitation, valid for five minutes:

```text
agentremote://pair#BASE64URL(JSON)
```

The JSON includes version 1, relay address, Mac routing fingerprint, invitation channel UUID, 32-byte random bootstrap secret (base64), expiry in Unix milliseconds, and display name. The URI fragment is decoded locally; the URI itself is never sent to the relay. Opening a deep link displays the pairing UI and requires the user to tap Pair Mac.

The phone creates an ephemeral X25519 key pair. It sends its raw public key and device name through an AES-GCM envelope protected by the bootstrap secret. The Mac creates its own ephemeral X25519 key pair and derives a shared secret. Inside a transaction, it consumes the invitation, issues a device UUID/API bearer token, and stores the resulting device key:

```text
deviceKey = HKDF-SHA256(
  IKM = X25519 shared secret,
  salt = 32-byte QR bootstrap secret,
  info = UTF8("agent-remote/pair/v1/" + host + "/" + deviceId),
  length = 32
)
```

The encrypted response contains the Mac’s ephemeral public key, device ID, bearer token, local host ID, and name. It does **not** contain the device encryption key. The phone independently derives the same key. Ephemeral private keys are not persisted. An expired QR secret alone cannot recover the subsequent device key from a recorded enrollment exchange.

The phone persists its device key and API token in Keychain, with `AfterFirstUnlockThisDeviceOnly` accessibility. The Mac stores its channel keys/identity in a directory restricted to its user (0700; SQLite file 0600). These keys are not stored in the cloud. This is not a ratcheting protocol: compromise of an established device key can expose recorded traffic for that device. Re-pairing produces a new key.

## Request envelopes

```json
{"v":1,"host":"64-char fingerprint","channel":"device-or-invite-uuid","id":"packet-uuid","issuedAt":0,"box":"BASE64"}
```

`box` is a 12-byte random nonce followed by AES-256-GCM ciphertext and its 16-byte tag. Fresh random nonces are generated by Node crypto / Apple CryptoKit. Request and response keys are derived separately:

```text
HKDF-SHA256(deviceKeyOrBootstrapSecret,
  salt = UTF8(host),
  info = UTF8("agent-remote/v1/" + channel + "/" + direction), length = 32)
```

`direction` is `request` or `response`. Authenticated additional data is:

```text
agent-remote/v1\nHOST\nCHANNEL\nPACKET_ID\nISSUED_AT\nDIRECTION
```

The encrypted request is `{method,path,token,body?}` or an initial `{op:"pair",name,publicKey}`. The encrypted response is `{status,body}`, with response body bytes base64 encoded so images and JSON share the same transport. Responses retain their request’s public header. The phone checks that the header matches the pending request before decrypting.

## Replay, retries and revocation

Both endpoints reject packets outside a two-minute clock window. The desktop inserts authenticated request IDs into a durable table before processing them and rejects repeated packet IDs. Receipts are retained longer than the packet acceptance window. Authentication failures do not consume request IDs.

Transport requests are never automatically resent after ambiguous delivery. Existing message-level `requestId` deduplication prevents a retried prompt from running twice even when it is wrapped in a new transport packet. Other mutations are not universally idempotent; inspect the resulting session after an ambiguous failure.

Revocation removes the device from the local authorization table and deletes its channel key. The desktop checks that table for every incoming packet; existing relay connections confer no authorization. Pairing secrets are single-use. A lost pairing response requires a fresh invitation.

## Availability and limits

- Mac reconnects with exponential backoff and jitter, capped around 30 seconds.
- Relay heartbeat terminates dead sockets. Mac checks for missing relay traffic.
- Phone connections are reused and recreated on failure or after a long idle period. Backgrounding does not stop Mac sessions.
- Relay caps connections, message size (40 MB), outstanding requests, pending bytes (64 MB), send backlog, connection attempts, and message rate; compression is disabled.
- The relay has no persistent message queue. Disconnected clients obtain current state from the Mac on reconnect.
- Initial deployment uses **one replica**. Multiple independent replicas cannot route to hosts connected to another replica; distributed routing is not implemented.
- Hosting ingress must support WebSockets, large frames, and TLS. Rate limiting at the edge is recommended for public operation. This application-layer protocol and relay have automated tests but have not received an independent security audit.

## Test evidence

`npm test` exercises encryption, binary transfer, authenticated host registration, tampering, replay, revocation, expired/used invitations, offline hosts, browser-origin rejection, and desktop reconnection. `scripts/test-native-relay.mjs` runs the iPhone’s actual Swift CryptoKit/URLSession implementation against Node endpoints, including the X25519/HKDF handshake and a 512 KB binary round trip.
