# Reply images and notifications

Registered PNG/JPEG/GIF/WebP image artifacts appear beside their response. Markdown image/file links render at their position; generated images without links attach to the response following file creation. Placement uses the entire conversation so paging does not move previews between messages. Paths in text never grant filesystem access. Tap an image for a full-screen viewer; pinch to zoom, drag to pan and double-tap to zoom/reset.

The iPhone gear menu has **Notifications**. Opt-in alerts notify once after a completed reply and once for each question that needs an answer, skip the currently visible conversation and open the session when tapped. Old history does not flood the phone on first enable; a question that is still waiting when notifications are enabled does alert. While the app is running, local reply alerts use the existing authenticated polling.

Two alert kinds leave the Mac. Their visible text is generic: "Your agent has replied." and "Your agent has a question for you." (time-sensitive); the readable details travel encrypted (see "What a notification contains" below). Question alerts cover native Claude questions in managed sessions and shared terminals (the question cards), Codex `requestUserInput`, the local `ask_question` tool, and questions shown by an independent desktop Claude client. The reply that introduced a question does not alert separately; the question alert replaces it on the lock screen (one collapse ID per session). Sessions the Mac does not stream itself (shared terminals, desktop Claude clients, Codex terminals) are refreshed every ten seconds when their transcript changes, so their replies and questions are noticed even while no phone is polling.

## Background delivery: Apple setup required

Locked-phone delivery uses APNs and cannot be implemented by keeping the phone's polling loop alive. The backend APNs sender, paired-device registration, deduplication, revocation checks and iPhone delegate are implemented. Two pieces are personal to the developer and are never packaged: the APNs signing key on the Mac, and an app build signed with a push-enabled profile.

For this developer's own Mac (team YA9PU25M2S, App Store bundle ID `com.agentremote.iphone`, which was registered with the Push Notifications capability on September 10, 2026):

1. Create the APNs signing key once: developer.apple.com → Account → Certificates, Identifiers & Profiles → Keys → **+** → name it (for example "Agent Remote push") → check **Apple Push Notifications service (APNs)** → Continue → Register → **Download**. The file is `AuthKey_<KEYID>.p8` and can be downloaded only once; keep it out of the repository and app bundle.
2. With that file in `~/Downloads`, run `python3 scripts/configure-push.py` (defaults: newest `AuthKey_*.p8` in Downloads, key ID from the file name, team YA9PU25M2S, topic `com.agentremote.iphone`; pass `--key`, `--key-id`, `--team-id`, `--topic` to override). The Mac service reads the configuration on demand; no restart is needed for the key itself, but the service must be a build that includes the notifier (Mac 0.7.2+, launched from `~/Applications/Agent Remote.app`).
3. Install a push-enabled iPhone build. TestFlight builds made with `scripts/release-ios.py --push` carry `aps-environment=production` and `AgentRemotePushEnvironment=production` (build 17 does). The Personal Team Preview build (`com.matthewslotkin.agentremote.preview`) cannot receive push. For device testing from Xcode use the paid team's development profile with `AGENT_REMOTE_APP_ENTITLEMENTS=AgentRemote/Push.entitlements APNS_ENVIRONMENT=development`. Since the Notification Service Extension target exists, do not pass `PRODUCT_BUNDLE_IDENTIFIER` or `CODE_SIGN_ENTITLEMENTS` on the command line (they would apply to the extension too); use `AGENT_REMOTE_BUNDLE_ID` (the extension becomes `<id>.NotificationService`) and `AGENT_REMOTE_APP_ENTITLEMENTS`.
4. In the iPhone app open the gear menu → Notifications and turn them on. The status line reads "Reply notifications are enabled, including when your phone is locked." once the device token is registered with the Mac. Then run `node desktop/src/admin.mjs push-test` on the Mac (or ask the agent to) to send a test alert, and verify that a real reply and a real question arrive on the lock screen and open the correct session.

The `.p8` and local config are never packaged. This direct Mac sender is for the developer's private setup. Public distribution must put developer APNs signing credentials in a hosted notification service rather than distributing them to users' Macs.

APNs payloads contain the generic alert text, a `kind` (`reply`, `question`, `test`, `auth`), opaque host/session IDs and, for reply and question alerts to relay-paired devices, the sealed `e2e` field described below. Nothing readable from the conversation or project reaches Apple or the relay. The Mac must remain running. Disabling notifications removes the device registration and its receipts; revoked paired devices are excluded. A device token Apple reports as unregistered is dropped and re-registered the next time the app enables notifications.

References: [Apple remote notification server](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server), [APNs token authentication](https://developer.apple.com/help/account/capabilities/communicate-with-apns-using-authentication-tokens/).

Background delivery remains unverified end to end until the APNs key exists on this Mac and the TestFlight build is installed on the phone; the sender, registration and question/reply detection are covered by backend tests.

## Push without a key on the Mac: the relay sender

When `push-config.json` is absent and the connected relay advertises `push` (see `docs/relay-deployment.md`), `GET /notifications/status` reports `configured:true`, and alerts go through the relay. The relay holds the developer's APNs key, so a user's Mac needs no Apple setup. The allowed topics come from the relay. The last advertised list is remembered in the settings table, so status does not flicker while the relay reconnects. An alert that cannot be sent (relay offline, timeout) is retried on the next ten-second tick, because no receipt is written. A local key, when present, always takes precedence. `admin.mjs push-test` only exercises the local-key path.

## What a notification contains, and answering from it

For every reply or question alert to a phone paired through the relay, the Mac also seals a small JSON object for that one device (`desktop/src/reply-notifications.mjs`, `sealPush`):

```json
{"v":1,"kind":"reply","session":"…","title":"<chat title, ≤64 chars>","body":"<first prose line of the reply, markdown stripped, ≤140 chars>","reply":true}
{"v":1,"kind":"question","session":"…","title":"…","body":"<question text, ≤200 chars, + \"(+N more)\">","question":{"id":"…","item":"…","options":["≤3 labels"]}}
```

It is encrypted with AES-256-GCM under a key derived from that device's existing relay E2E secret (HKDF-SHA256, salt = host ID, info `agent-remote/v1/push`, so it never equals a request/response key), with the host ID, session ID and kind as authenticated data. The result (`nonce | ciphertext | tag`, base64, at most 1,500 characters; option buttons are dropped first, then the text shortened, if it would not fit) is sent as `e2e` beside the unchanged generic alert, with `aps.mutable-content: 1`. Both delivery paths carry it: the Mac's own APNs key builds the payload directly, and the relay sender accepts `e2e` (base64, 40–1,500 chars, only with `mutable-content: 1`, a host ID and a session, never for `auth`) and passes it through without logging it. A relay without this support ignores the field and sends the generic alert. Directly paired phones (no relay secret) get the generic alert only.

On the iPhone, the Notification Service Extension (`ios/AgentRemoteNotificationService`, iOS only; the Mac Catalyst client does not embed it) reads the per-Mac secret from the shared Keychain group `$(AppIdentifierPrefix)com.agentremote.shared`, decrypts, checks that the content matches the visible session and kind, and replaces the title and body. Any failure (missing key, wrong device, tampering, timeout) leaves the generic alert. The app moves secrets saved by earlier builds into the shared group at launch, deleting the old copy only after the shared copy reads back identical; builds without the keychain-sharing entitlement (no push) keep using the app's own group.

Actions: reply alerts for chats the phone can type into get a **Reply** text field; single-item questions get one button per option (up to three; each distinct option set is registered as its own notification category just before the alert is shown) plus **Answer…** for free text, falling back to **Answer…** and **Open** if the category cannot be registered. Multi-item and read-only questions only open the chat. All actions require the phone to be unlocked. The app, launched in the background if needed, sends the answer through the usual encrypted API path (`POST /sessions/:id/questions/:qid/answer` or `POST /sessions/:id/messages`) and posts a local "wasn't sent" alert, which opens the chat, if the Mac cannot be reached.
